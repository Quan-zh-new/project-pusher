# Skills 设计说明

## 1. 定位

Skill 是面向开发者/Agent 的可复用操作指南，不是模型在一次对话中自动拥有的隐式能力，也不是替代 Tool Schema 的业务脚本。它用于沉淀跨任务可重复的工程流程、环境前置条件、验证步骤和安全边界。

项目内现有验收类 Skill 可用于 Agent、数据回收、恢复、媒体和最终交付的端到端验证。任何 Skill 的具体路径、前置工具和运行命令都应以当前仓库实际文件为准。

## 2. 适合沉淀为 Skill 的内容

- 多次出现且步骤稳定的 E2E 验收流程。
- 外部 CLI 的授权检查、最小安全调用、结果读取回验。
- 受管媒体处理、状态审计、故障定位等跨领域操作。
- 新模块的统一脚手架、测试模板和文档更新步骤。

不适合：一次性项目数据、临时 URL、某个任务的具体结论、需要模型基于当前 Context 自主判断的规划决策。

## 3. Skill 结构与原则

每个 Skill 应有清晰的 `SKILL.md`，至少说明：触发场景、目标/非目标、前置条件、输入输出、操作顺序、验证证据、失败处理和安全限制。脚本应仅封装机械且可测试的步骤；任务分支、用户意图理解、Plan 生成和 Artifact 选择仍应留给模型+Context+Tool Contract。

优先提供通用参数与示例，不写“若出现某句用户话术就执行某流程”的规则。需要硬限制（权限、轮次、破坏性操作、密钥）时由运行时或工具层保证，Skill 负责告知和验证。

## 4. 接入当前项目的方式

1. 先确认 Skill 是否补足了重复工程流程，而不是重复一个已有 Tool。
2. 明确它服务的层：开发验收、外部 CLI、数据处理或交付验证。
3. 如果运行时要调用其能力，仍要通过明确 Tool Schema 暴露原子动作；不能让模型执行任意 Skill 脚本。
4. 在相关设计文档与 `instruction.md` 记录入口、适用范围和验收标准。
5. 用真实或受控替身跑通成功、失败、权限不足和部分结果路径。

## 5. Skill 变更验收

修改 Skill 后验证其命令在干净条件下可执行、不会泄露密钥或写入未授权目标、输出能被 Run/Plan/Artifact 审计引用，并且不与 System Prompt、Tool、Memory、Plan 的职责重叠。

## 6. CLI Help 与 Skills

`inspect_cli_help` 只用于查询真实 CLI `--help`，结果由缓存复用以减少重复调用；不会写入 `skills/`，也不会生成跨 Run 的 CLI Skill。

## 7. 文件树 Skill 库

项目根目录 `skills/` 是 Skill 正文的唯一来源。页面仅审阅已有文件并允许用户向已选父 Skill 上传 Markdown 子 Skill；上传内容不能成为可执行脚本或默认 Prompt。运行时通过 `search_skills` 按需检索，模型仍自行决定具体后续工具调用。

## 8. 文件树 Skill 来源与 Run 绑定

运行时 Skill 正文的唯一来源是项目根 `skills/`。每个父目录必须有且只有一个顶层 `.md` 父 Skill（文件名任意）；`references/**/*.md` 是可选子 Skill。`search_skills` 是唯一检索工具：未传 `parentSkillPath` 返回父 Skill，传父文件的相对路径后返回该目录的子 Skill。非空 `query` 按空白拆词，候选的标题、摘要和正文只要包含任一词就允许返回；没有任何词命中的候选必须过滤。相对路径和不带 `.md` 的文件名也是检索身份字段：完整路径/文件名命中优先，其次是文件名或路径词命中，最后才是完整 query 或正文词命中，避免“引用某个 Skill 的工作流”排在该 Skill 本体之前。父或子命中后服务端自动冻结文件快照到当前 Run，并只在该 Run 后续 Context 注入。不能传任意文件路径、不能跨父目录混选、不能自动继承到新 Run。
